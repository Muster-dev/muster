# Rollouts: blue-green, canary and version visibility

muster can roll a Kubernetes service out gradually instead of replacing it in
one go:

- **blue-green**: the new version comes up next to the old one with 0% of the
  traffic. You (or a gate) check it, then one Service selector change moves all
  traffic over. Switching back is just as quick.
- **canary**: the new version gets a slice of the traffic (10% → 25% → 50% →
  100% by default). Health gates run at every step; a failing gate sends all
  traffic back to the stable version.
- **rolling** (the default): your hook's normal `kubectl` rollout. muster shows
  which version every live ReplicaSet runs and how much traffic it carries
  while it rolls.

There's nothing to install in the cluster: no CRDs, no controller. muster uses
standard Deployments, Services and one ConfigMap per service, through the
`kubectl` you already use.

> Phase 1 covers Kubernetes. Docker/Compose hosts, Gateway API / ingress-nginx
> weights and metric gates are planned (see [What's next](#whats-next)).

## How it works

| Who | Does what |
|-----|-----------|
| Your deploy hook | builds and pushes the image, then points the **target** Deployment (`$MUSTER_TARGET_DEPLOYMENT`) at `$MUSTER_IMAGE_TAG` |
| muster's rollout engine | creates the candidate Deployment, scales it, runs the gates, shifts traffic, promotes or aborts, and records the state |

During a blue-green or canary deploy muster sets these variables for the hook:

| Variable | Example | Meaning |
|----------|---------|---------|
| `MUSTER_STRATEGY` | `canary` | `rolling`, `blue-green` or `canary` |
| `MUSTER_DEPLOY_VERSION` | `v1.4.2` / `4f2a9c1` | version label for this deploy (also set for rolling) |
| `MUSTER_IMAGE_TAG` | `v1.4.2` | tag to build/push. Rolling: `$IMAGE_TAG` or `latest`, same as before. Blue-green/canary: `$IMAGE_TAG` if it's set and not `latest`, else the version, because both versions run side by side and need different tags |
| `MUSTER_TARGET_DEPLOYMENT` | `acme-api-canary` | the Deployment to update |
| `MUSTER_K8S_DEPLOYMENT` | `acme-api-canary` | same as the target, so existing hooks that use it work unchanged |
| `MUSTER_K8S_BASE_DEPLOYMENT` | `acme-api` | the Deployment named in muster.json |
| `MUSTER_ROLLOUT_TRACK` | `canary` / `green` | track being deployed |
| `MUSTER_STRATEGY_TRAFFIC` | `replicas` | traffic mechanism |
| `MUSTER_K8S_CONTAINER` | `api` | `k8s.container` from muster.json, when set |

A hook generated by `muster setup` for k8s already works. It runs
`kubectl set image deployment/$MUSTER_K8S_DEPLOYMENT …`, which now points at
the candidate. The strategy templates (below) also skip `kubectl apply` of your
manifests: re-applying them mid-rollout would reset the stable Deployment and
the Service selector.

**Version.** The version comes from `--version`, then `MUSTER_DEPLOY_VERSION`,
then `IMAGE_TAG` (unless it's `latest`), then an exact git tag, then the short
git SHA, and finally a timestamp. A label-safe copy goes on the pods as
`muster.dev/version`.

**State.** Each service's rollout is kept in `ConfigMap/muster-rollout-<deployment>`
(label `muster.dev/rollout=true`) in its namespace. A laptop, a CI job and
muster-tui all see the same rollout as long as they can reach the cluster.

**Labels.** Candidate pods get `muster.dev/track` (`blue`, `green` or
`canary`), `muster.dev/version` and `muster.dev/service`.

## Configuration

Add `strategy` to a service in `muster.json`. Leaving it out means `rolling`.

```json
"api": {
  "name": "API",
  "k8s": { "deployment": "acme-api", "namespace": "prod" },
  "strategy": {
    "type": "canary",
    "steps": [10, 25, 50, 100],
    "pause": "manual"
  }
}
```

Shorthands: `"strategy": "canary"` uses all the defaults, and each entry in
`steps` can be a number (`25`) or an object (`{"weight": 25, "pause": 120}`).

| Field | Values | Default | Notes |
|-------|--------|---------|-------|
| `type` | `rolling`, `blue-green`, `canary` | `rolling` | blue-green/canary need `k8s.deployment` |
| `traffic` | `auto`, `service-selector`, `replicas` | `auto` | auto = service-selector (blue-green), replicas (canary). `gateway-api`, `ingress-nginx`, `traefik`, `caddy`, `nginx` and `caddy-managed` are reserved for later releases and rejected for now |
| `steps` | weights 1-100 (increasing), or `{weight, pause}` | `[10, 25, 50, 100]` | canary only; a final 100 is added (with a warning) if you leave it out |
| `pause` | seconds or `"manual"` | `60` (canary) | default pause for every step except 100 |
| `auto_promote` | `true` / `false` | `false` | blue-green: switch traffic as soon as the gates pass |
| `drain_seconds` | 0-3600 | `30` | wait after switching traffic before scaling the old version down |
| `keep_old_seconds` | -1, 0-86400 | `0` | blue-green: keep the old colour running (warm rollback); it's scaled down on the next deploy once the time has passed. -1 keeps it until the next deploy |
| `auto_rollback` | `true` / `false` | `true` | when a gate fails, restore stable. With `false` the rollout is left `degraded` for you to look at |
| `on_interrupt` | `abort` / `pause` | `abort` (canary), `pause` (blue-green) | what Ctrl+C does mid-rollout (see below) |
| `preview.enabled` | `true` / `false` | `false` | blue-green: also create a `<service>-preview` Service that selects the new colour |
| `preview.service` | name | `<service>-preview` | |
| `analysis.interval_seconds` | 1-300 | `10` | time between gate checks |
| `analysis.max_failures` | 1-20 | `2` | consecutive health failures before the gate fails |
| `analysis.health_check` | `true` / `false` | `true` | run `health.sh` against the candidate |
| `analysis.pod_stability` | `true` / `false` | `true` | fail at once on CrashLoopBackOff, image pull errors, OOMKilled, config errors |
| `analysis.max_restarts` | 0+ | `0` | candidate container restarts allowed |

Other k8s keys used by strategies:

| Key | Default | |
|-----|---------|---|
| `k8s.service` | `k8s.deployment` | the Service that carries production traffic |
| `k8s.container` | first container | container to report (and to update in the templates) |

`muster` checks all of this when it loads the config (the same checks show up
in `muster doctor`). Fields that belong to later phases (`analysis.prometheus`,
`analysis.http_probe`, `analysis.command`, `proxy`) produce a warning and are
ignored for now.

### Switching an existing project

```bash
muster setup --update --strategy api=canary      # or api=blue-green / api=rolling
muster hooks approve api
muster deploy api --dry-run                      # shows the step plan
```

This writes the strategy into muster.json and regenerates `api`'s hooks from
`templates/hooks/k8s/canary/`. A hook you edited is kept as it is; the new
template is written next to it as `deploy.sh.strategy-new`, so you can copy in
the two lines that matter (`MUSTER_TARGET_DEPLOYMENT`, `MUSTER_IMAGE_TAG`). A
fresh `muster setup --stack k8s --services api --strategy api=canary` does the
same at setup time.

## Commands

```bash
muster deploy api                       # uses the strategy from muster.json
muster deploy api --strategy canary     # this run only (rolling, blue-green, canary)
muster deploy api --version v1.4.2      # version label (default: tag / SHA)
muster deploy api --no-wait --json      # CI: start it, stop at the first step, exit 0

muster rollout status [api] [--watch] [--interval 3] [--json]
muster promote api                      # canary: next step; blue-green: switch traffic
muster promote api --to 50              # canary: go to 50% and pause there
muster promote api --full               # straight to 100%
muster abort api                        # 100% back to stable, candidate scaled to 0
muster rollback api                     # see below
```

`promote` and `abort` ask for confirmation in a terminal. `--yes` skips the
question, and so do `--json` and running without a TTY. Both take the deploy
lock, like `deploy`.

When a rollout pauses (a manual step, a blue-green preview, or `--no-wait`):

- in a terminal, `muster deploy` offers **Promote / Abort / Keep paused**
- otherwise it exits 0 with the service result `paused`, releases the lock,
  and you continue later with `muster promote` / `muster abort` (from any
  machine that can reach the cluster)

A new `muster deploy` of a service with a paused rollout is refused (exit 1,
`reason: rollout_in_progress`). `deploy --force` aborts the paused rollout
first.

### Rollback

`muster rollback <svc>` checks the rollout state first:

| State | What rollback does |
|-------|--------------------|
| rollout in progress (paused, awaiting promotion, degraded) | same as `muster abort` |
| completed blue-green | switches the Service back to the previous colour, scaling it up first if it was scaled down (warm = instant), then scales the bad colour to 0 |
| completed canary, rolling, anything else | runs `rollback.sh` as before (`kubectl rollout undo` on the stable Deployment, which holds the new version after a canary promotion) |

### Ctrl+C

Pressing Ctrl+C (or sending SIGTERM) mid-rollout never leaves traffic stuck on
an unmonitored candidate:

- **before any traffic moved** (hook running, candidate starting, blue-green
  gates): the candidate is scaled to 0, except with blue-green
  `on_interrupt: pause` and a candidate whose gates passed, which stays up
  awaiting promotion
- **canary with traffic split**: `on_interrupt: abort` (default) restores 100%
  stable. `pause` keeps the current weight if the canary's last gate passed
  (otherwise it aborts anyway)
- **blue-green right after the switch, before the post-switch check passes**:
  the Service is switched back

After that muster records `cancelled` in the history, emits
`{"event":"cancelled","service":…,"safe_version":…,"exit_code":130}` in
`--json` mode, releases the locks and exits 130.

## What happens on the cluster

### Blue-green (`service-selector`)

1. **First deploy only (adoption):** `acme-api` is copied to `acme-api-blue`
   with `muster.dev/track=blue`. Once blue is ready, the Service selector gets
   `muster.dev/track: blue` and the original Deployment is scaled to 0 (kept
   for reference). Both serve traffic during the copy, so nothing drops.
2. The inactive colour (`acme-api-green`) is (re)created from the live one at
   0 replicas, the hook points it at the new image, then muster scales it to
   the live replica count and waits for it to be ready.
3. Optional preview Service → green. Gates run against green.
4. `awaiting_promotion` (or straight on with `auto_promote`).
5. **Promote:** one `kubectl patch service` changes the selector to green, and
   the gates run again against production. If they fail, the selector goes back
   to blue (`auto_rollback`). After `drain_seconds` blue is scaled to 0 (or
   kept warm for `keep_old_seconds`).

### Canary (`replicas`)

The stable `acme-api` and `acme-api-canary` both match the Service, so traffic
follows the ratio of ready pods. For weight W with N stable replicas (at
least 2):

```
canary = ceil(N × W / 100)   (at least 1)
stable = N − canary          (at least 1)
```

The canary is scaled up before the stable is scaled down, so capacity never
drops. Each step reports the **target** weight and the **effective** weight
(ready canary pods / all ready pods). With few replicas these differ: 10% of 2
pods is really 50%, and `rollout status` shows `(target 10%)`. Use more
replicas (or, later, Gateway API) when you need fine-grained weights.

At 100% the canary's image is copied onto the stable Deployment, which rolls
out normally. Once it's ready the canary is scaled to 0. Abort scales the
stable back to its original size first, then the canary to 0.

Caveats:

- The canary Deployment's pods also match the stable Deployment's selector.
  Kubernetes handles this through owner references (each ReplicaSet only
  manages its own pods), but it's the same overlap the docs warn about.
  Weighted routers (Phase 2) avoid it.
- An HPA on the stable Deployment fights the replica ratio. `muster doctor`
  warns about it.
- Old and new versions run side by side: use expand-and-contract database
  migrations.

### Rolling

Nothing changes in how rolling deploys run. muster now also:

- passes `MUSTER_DEPLOY_VERSION` / `MUSTER_IMAGE_TAG` to the hook. The
  generated rolling template stamps `muster.dev/version` on the pod template in
  the same patch as the image (one ReplicaSet revision)
- lists every live ReplicaSet with its revision, version (label, else image
  tag), image, ready/desired and traffic share in `status --json`
  (`rollout` while more than one ReplicaSet has pods) and `rollout status`

## Gates (Phase 1)

| Gate | Fails when |
|------|------------|
| `pod_stability` | a candidate pod is in CrashLoopBackOff, ImagePullBackOff, ErrImagePull, ErrImageNeverPull, InvalidImageName, CreateContainerConfigError, RunContainerError or OOMKilled, or restarts more than `max_restarts`. Fails at once |
| `health` | `.muster/hooks/<svc>/health.sh` exits non-zero `max_failures` times in a row. It runs with `MUSTER_K8S_DEPLOYMENT` / `MUSTER_TARGET_DEPLOYMENT` set to the candidate and `MUSTER_ROLLOUT_TRACK` set |

Timed steps (`"pause": 120`) run the gates every `interval_seconds` for the
whole pause. Manual steps run them once (retrying up to `max_failures`) before
pausing.

## Output

Human output (`rollout status`, `status`, during `deploy`):

```
  api  CANARY · replicas   step 1/3 · 41s
    v1 stable 3/3   75%  [#####---------------]   25%  v2 canary 1/1
    State: paused — next: 50% (muster promote api · muster abort api)
    Gates: ok pod_stability  ok health
```

JSON: see [ENGINE-API.md](ENGINE-API.md) (`rollout status --json`, `promote` /
`abort --json`, the `rollout_step` / `traffic_shift` / `analysis` /
`promoted` / `aborted` events, and the new `status` / `history` / `summary`
fields).

## Requirements

- `kubectl` with access to the namespace: get/create/patch on Deployments,
  Services and ConfigMaps, get on ReplicaSets and Pods. `muster doctor` checks
  this with `kubectl auth can-i`.
- `jq`.
- Remote services (`remote.enabled`) run the engine's `kubectl` calls over
  key-based SSH. Fleet Cloud remotes and password SSH aren't supported for
  strategies yet. `status --json` only reads versions with a local kubectl;
  `rollout status` also works for remote services.

## Compared with other tools

|  | muster | Argo Rollouts | Flagger | Kamal 2 |
|--|--------|---------------|---------|---------|
| Runs on | Kubernetes today; Docker hosts planned | Kubernetes | Kubernetes | Docker hosts over SSH |
| Cluster install | none (kubectl + 1 ConfigMap per service) | controller + CRDs | controller + CRDs (+ metrics backend) | n/a (`kamal-proxy` on each host) |
| Workload | your existing Deployment | `Rollout` CRD instead of `Deployment` (or `workloadRef`) | your Deployment, wrapped by a `Canary` CRD | containers |
| Blue-green | Service selector swap + preview Service | active/preview Services | yes (via mesh/ingress) | the deploy itself is a zero-downtime swap; no held preview |
| Canary weights | replica ratio (target + effective weight reported); Gateway API / ingress-nginx planned | many traffic routers (Gateway API plugin, NGINX, Istio, ALB, …) | Gateway API, Istio, Linkerd, NGINX, … | not exposed as a stepped workflow |
| Gates | pod stability + your `health.sh`; Prometheus/HTTP/custom gates planned | AnalysisTemplates (Prometheus, Datadog, Web, Job, …) | MetricTemplates (Prometheus, Datadog, CloudWatch, …) | HTTP readiness check |
| Promote / abort | `muster promote` / `muster abort`, from CLI, CI (`--json`) or any machine reaching the cluster | `kubectl argo rollouts promote/abort`, UI | automated loop (GitOps) | `kamal rollback` |
| Version visibility | per-version replicas, weights, revision in CLI and JSON, also for plain rolling updates | `kubectl argo rollouts get rollout --watch`, UI | `kubectl get canary`, events | `kamal app details` |

Argo Rollouts and Flagger have many more traffic routers and analysis
providers and run as in-cluster controllers. muster's strengths are that it
needs no cluster install, keeps your Deployments as they are, and works from
the same CLI and JSON API you already use.

## What's next

Not implemented yet. This is the plan; details may change.

**Phase 2: weighted routers and metric gates (Kubernetes)**
- `traffic: gateway-api`: patch `HTTPRoute` `backendRefs` weights between
  `<svc>-stable` / `<svc>-canary` Services (created by muster); auto-detected
  when an HTTPRoute references the Service
- `traffic: ingress-nginx`: companion canary Ingress with
  `nginx.ingress.kubernetes.io/canary-weight` (with a notice that ingress-nginx
  was retired in March 2026)
- gates: `analysis.http_probe` (status + latency), `analysis.prometheus`
  (PromQL threshold via curl + jq + awk, `treat_no_data`), and a trust-approved
  `.muster/hooks/<svc>/gate.sh`
- `muster rollout pause|resume`, `rollout history`, `rollout init` (adopt
  without deploying)
- doctor: stale `muster-rollout-*` ConfigMaps, orphaned `-canary` Deployments,
  GitOps (Argo CD / Flux) annotations on the Service

**Phase 3: Docker / Compose hosts**
- blue/green slots (`<svc>-blue` / `<svc>-green` on alternating loopback
  ports) with state in `.muster/rollouts/<svc>.json`
- proxy adapters: Traefik file provider, Caddy admin API, NGINX upstream
  snippet with `nginx -t` + `.bak` restore, and an optional `caddy-managed`
  container
- weighted canary through the proxy; warm rollback (`docker start` the old
  slot)
- `templates/hooks/{docker,compose}/blue-green/`, `muster fleet promote|abort|rollout status`

**Clients**
- muster-tui rollout card (dashboard strip + service screen, `p`/`P`/`a`/`w`
  keys, ASCII fallback), detected via `muster --help` listing
  `rollout`/`promote`/`abort`
- Muster Assistant / `bin/muster-mcp` tools `muster_rollout_status` (read) and
  approval-gated `muster_promote` / `muster_abort`; muster-agent allowlist for
